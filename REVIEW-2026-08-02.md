# Medebirr (e-Merkato) — Full-Stack Review

**Date:** 2026-08-02 · **Commit reviewed:** `e4990916` (main HEAD) · **Reviewer:** Arena Agent
**Scope:** frontend, backend, APIs, security, UX paths, broken paths, dead code, strengths/weaknesses, test strategy, roadmap.

---

## 1. Executive Summary

Medebirr is an ambitious Telegram-mini-app marketplace for Ethiopia: vanilla-JS SPA frontend, Express backend (Vercel serverless), Postgres (Supabase), three Telegram bots (main/scraper/search), Telebirr/CBE/M-Pesa/cash payments, QR-based dual-confirmation delivery, group buys, coupon-led social commerce, OCR-assisted receipt verification, and a nearly-complete i18n pipeline (Amharic pending translation).

**Verdict: NOT production-safe today.** The codebase is well-organized and clearly improving, but I found:

- **1 boot-breaking bug at HEAD** (backend could not start at all) — *fixed in this session*;
- **3 critical business-logic holes** that let any user get free orders, self-confirm "delivered" on other people's orders, or run JS in other users' sessions;
- A payment architecture that **contradicts itself**: a careful "seller confirms receipt" bot flow exists, but the in-app checkout marks orders paid *before* any verification, making the safe flow unreachable;
- Very solid foundations in other areas: parameterized SQL throughout, proper HMAC initData verification with timing-safe compare, transactions + row locking on stock, idempotency guards against double stock deduction, structured logging, env validation.

**Immediate actions:** deploy the stores.js fix, gate `confirm-tx`/`cash/confirm`, add party-checks to delivery routes, escape user-generated strings in `buyer.js`, and fix `vercel.json` CORS.

## 2. Severity Findings (Critical → High)

### 🔴 P0-1 — Backend did not boot at HEAD (FIXED in this session)
`backend/src/routes/stores.js:226` — an unterminated `const {` destructuring in `PUT /:storeId` made Node throw `SyntaxError: Unexpected identifier 'result'` at require time. Every `/api/*` call on Vercel would return 500 `FUNCTION_INVOCATION_FAILED`. This exact class of outage is already documented in `JOURNAL.md` (the pino incident) — same root cause: **no pre-merge smoke test ran**.
**Fix applied:** restored the destructuring block; `stores.js` parses, and the full suite (35 tests) now passes.
**Systemic fix:** run `node -e "require('./src/app').createApp()"` + `npm test` in CI on every PR (see `.github/` — no workflow currently enforces this, and `app.test.js` would have caught it).

### 🔴 P0-2 — Manual payments are auto-confirmed by the buyer (fraud by design)
`public/js/views/checkout.js:791` — after creating an order the SPA immediately calls:
```js
await Api.payments.confirmTx(order.order_id, this._txCode || `TXN-${Date.now()}`, proof);
```
`POST /payments/confirm-tx` (`routes/payments.js`) → `markOrderPaid()` sets `payment_status='paid'`, `order_status='confirmed'`, deducts stock, and Telegram-notifies the seller "💰 Payment Received! … Please prepare for dispatch." The TX code is **optional** — if empty, the frontend *fabricates* `TXN-<timestamp>`. Nothing validates the code against Telebirr/CBE.
Consequences:
- A buyer can order anything, pay nothing, and the seller is told to dispatch.
- The careful verification-bot flow (`handleReceiptPhoto` → seller presses "Confirm Payment" → `markOrderPaid`) is **dead code for in-app orders**: by the time the seller gets the receipt, the order is already paid and `handleConfirmPayment` early-returns "Already paid".
- Same for cash: `POST /payments/cash/confirm` lets the **buyer** mark their own COD order paid+confirmed at checkout time, before any delivery.
**Fix:** `confirm-tx` and `cash/confirm` should only record *intent* (`payment_status='verifying'`, order stays `pending`); only the seller bot-confirm, the signed Telebirr webhook, or an explicit seller COD-collected action may call `markOrderPaid`.

### 🔴 P0-3 — Delivery verification is an unauthenticated-in-spirit IDOR chain
`backend/src/routes/delivery.js` — every route checks only `requireAuth`, never whether the caller is the buyer, the seller, or an assigned rider:
- `GET /delivery/:orderId/qr` returns `qr_data` **including the secret `v` token** to anyone;
- `POST /:orderId/scan` trusts caller-supplied ` scanned_data` and `scanner_role` — the same attacker can submit **both** `rider` and `buyer` scans on *any* order → order flips to `delivered`, `inventory.completeDelivery()` releases stock and credits store revenue;
- `POST /:orderId/verify-otp` (4-digit code, **no attempt cap on this route**) and `verify-code` (5 attempts tracked but never locks);
- `POST /:orderId/return` cancels anyone's dispatched order and releases stock;
- `GET /:orderId/receipt` exposes buyer name, phone, full address (PII).
Order IDs are UUIDs (hard to guess) but they leak via receipts, QR screenshots, and Telegram deep links. Contrast with `orders.js`, which consistently checks `buyer_tg_user_id`/`admin_tg_user_id` — the delivery router predates that discipline.
**Fix:** derive allowed roles from the order row (buyer = `buyer_tg_user_id`; rider/seller side = `admin_tg_user_id` or a matched `rider_phone`), enforce per-route; cap OTP attempts globally; never return `qr_data.v` to anyone but the buyer.

### 🔴 P0-4 — Stored XSS in the buyer feed → account takeover
`public/js/views/buyer.js` interpolates raw seller-controlled strings into `innerHTML` — e.g. `${p.title}` (lines 72, 102, 1295), `${s.store_name}` (173, 274), and `checkout.js` embeds `telebirr_merchant_id` inside an inline `onclick="CheckoutPage._copyText('${telNum}',…)"` handler. A product titled `<img src=x onerror="fetch('/api/v1/users/me',{headers:{Authorization:'Bearer '+localStorage.em_token}})">` executes in every buyer's session. The JWT lives in **`localStorage.em_token`**, so XSS = full account theft; helmet is loaded with `contentSecurityPolicy: false`. The escaping helper `_escapeHtml()` exists only in `modals.js` and is used for only a handful of PDP fields.
**Fix:** one global `esc()` used by *every* template (or a tagged-template helper), drop inline event handlers, and re-enable a CSP with `script-src 'self' telegram.org unpkg.com`.

### 🔴 P0-5 — `vercel.json` wildcard CORS fights the Express allow-list
`vercel.json` adds `Access-Control-Allow-Origin: *` to every `/api/*` response while `app.js` implements a careful origin allow-list (`FRONTEND_URL`, medebirr.vercel.app, preview regex, `credentials: true`). The result is duplicate/conflicting ACAO headers — browsers reject credentialed responses with `*` and duplicates — and the edge header makes the Express logic moot.
**Fix:** delete the `headers` block from `vercel.json`; let Express own CORS.

### 🟠 P1-1 — Telebirr webhook verification can be switched off by an ops flag
`payments.js` webhook: `const isTesting = NODE_ENV==='test' || BYPASS_TELEGRAM_AUTH==='true'` skips signature verification. `BYPASS_TELEGRAM_AUTH` is documented as something to toggle in hosted environments for browser testing — if it ever coexists with a live Telebirr `notifyUrl`, anyone can POST `{"outTradeNo":"TBX-…","tradeStatus":"SUCCESS"}` and get orders marked paid. Also in that handler: no amount-vs-order comparison, non-timing-safe `!==` signature compare, and it mutates `req.body` via `delete payload.sign`.
**Fix:** never bypass signature verification when `TELEBIRR_APP_SECRET` is set; compare with `crypto.timingSafeEqual`; verify `totalAmount === order.total_etb`.

### 🟠 P1-2 — Phone OTP "verification" verifies nothing, and its brute-force counter is dead code
`services/otp.js` sends the code to the user's *own Telegram chat* (`sendOtp(req.user.tg_user_id, phone)`), so any user can "verify" any phone number they type — it proves no ownership of the phone number. Separately, `verifyOtp()` looks up rows by `(tg_user_id, phone, code)`: wrong guesses match no row, so `attempts` is **never incremented** and `MAX_ATTEMPTS=3` can never trigger. Code space is 16⁶ hex — only the global rate limit (300 req/15 min/IP) slows brute force.
**Fix:** increment attempts on a "(user, phone) latest active code" row regardless of match; consider Telegram contact-share (`request_contact`) instead of self-DM codes.

### 🟠 P1-3 — Order idempotency key is stored in a column that payments later overwrite
`orders.js` POST stores `idempotency_key` in `payment_tx_ref` — but `payments.js` `/telebirr/initiate` and `confirm-tx` both `UPDATE orders SET payment_tx_ref=…` afterwards. A retried checkout after payment initiation **creates a duplicate order**. The lookup is also racy (check-then-insert, no unique index).
**Fix:** dedicated `idempotency_key` column with `UNIQUE(buyer_tg_user_id, idempotency_key)`; return the existing order on conflict.

### 🟠 P1-4 — Paid-order cancellation has no refund ledger
Buyer `PATCH /orders/:id/cancel` allows cancelling `confirmed` (i.e., paid) orders: stock is released, order closed, **money stays with the seller, no refund record**. Seller `mark-refunded` sets `payment_status='refunded'` but inserts no compensating row in `payment_transactions` — no financial audit trail. `cancel-request` can also be spammed (no dedupe) to flood a seller's Telegram.
**Fix:** state machine: `paid → refund_requested → refunded|rejected`, with ledger rows; rate-limit cancel-request per order.

### 🟠 P1-5 — Stores are born "verified"
`POST /stores` inserts `status='verified'` immediately; ordering only requires `status IN ('verified','active')`; there is a `kyc_document_url` column and a `seller_verifications` table but nothing gates selling on them. Anyone can spin up unlimited instant storefronts (also unbounded: no per-user store limit), list products, receive "paid" orders (see P0-2), and disappear.
**Fix:** `pending` default → basic checks → `verified`; cap stores per user; surface `verification_tier` in the buyer UI (the data model already supports it).

## 3. Frontend POV

**Stack:** single `public/index.html`, 14 plain `<script>` files (no bundler), inline-style-heavy template rendering, Leaflet + html5-qrcode from unpkg, Telegram WebApp script.

**Strengths**
- Optimistic two-phase boot (`_restoreCache()` → render → background auth) — feels instant; graceful offline/demo fallback.
- Cache-busting is semi-automated (`scripts/bump-cache.js` embeds git SHA into `?v=`).
- i18n architecture is genuinely good: catalog generator, delta CSVs, `State.t()` everywhere in buyer/checkout/seller, 549/549 keys resolve (validated with `scripts/validate-i18n.js`).
- Consistent design system tokens in one `app.css`; dark/light themes.
- Cart keyed per store with server-side re-pricing at order creation (client prices are display-only — correct).

**Weaknesses**
- **XSS surface everywhere** (P0-4): 22–38 `innerHTML` writes per view file, escaping is opt-in and rarely used.
- **No router**: state lives in memory + query params; two deep links handled (`complete_*`, `product_*`) but Telebirr `returnUrl /order-complete?order_id=` and the dev `mock-payment` URL are referenced by the backend and handled by **nothing** → broken round-trip after real Telebirr payment.
- Unbundled, unminified; unpkg CDN deps **without SRI** — one compromised CDN ships JS into every session (CSP is off, remember).
- JWT in localStorage (XSS-exfiltratable); 7-day tokens, no refresh/revocation story.
- 15s polling while on orders/dispatch tabs — scoped to visible tabs (good) but no `document.visibilitychange` pause.
- `State.languages` includes `'or'` (Afaan Oromoo) and `i18n.js` looks for `window.I18N_or`, but **no `or.js` exists** and `index.html` doesn't load one — silently dead language option; Amharic is 12/1048 strings translated (fallback to English works, so the switcher currently ships an empty language).
- `handleSearch` fires per keystroke with client-side filtering only — fine now, will need server search + debounce at catalog scale.
- Demo-data fallback (`_demoProducts`) can mask real outages behind a believable UI.

## 4. Backend POV

**Strengths**
- Shared `createApp()` factory so Vercel (`api/index.js`) and local (`server.js`) can't drift — and a test that guards it.
- Parameterized SQL everywhere I checked — **no injection findings**.
- Correct Telegram initData verification: HMAC with `WebAppData`, timing-safe compare, 24h `auth_date` window.
- Real concurrency hygiene on money paths: `FOR UPDATE` stock locking, transactions, reserved-vs-actual stock split, deadlock retry wrapper, explicit double-deduction guards (regressions from the last incident are fixed).
- Startup env validation with hard-fail in prod; webhook secret enforced in prod; per-route ownership checks in most of `orders.js`/`stores.js`/`products.js`/`social.js`.
- Full-text search (tsvector+GIN) with a migration, TTL caches with invalidation on writes, pino request logging with request IDs.

**Weaknesses**
- **Boot regression at HEAD** (P0-1) — process-level quality gate missing.
- **The `dal/orders.js` layer is half-adopted** (only `delivery.js` uses it); `orders.js` still hand-writes the same queries the DAL abstracts — two sources of truth for the same SQL.
- **Two logging systems**: pino in infra files, `console.warn/log` all over `payments.js`, `bot.js`, `orders.js` — logs will be unstructured exactly where money moves.
- **The two-package.json trap is still live**: `tesseract.js` is in root `package.json` but missing from `backend/package.json` (the exact failure mode the JOURNAL documented for pino). Local `npm test` in backend only passed because the OCR module isn't required in tests.
- OCR (`tesseract.js`) runs **synchronously inside the bot webhook** — heavy WASM on a serverless function that must ACK fast; move to a queue/deferred path (already flagged in the July audit, still open).
- PDF receipt + Telegram document delivery also runs inline in the Telebirr webhook — webhook latency risk.
- Rate limiting is per-instance in-memory (fine at 1-2 lambdas, ineffective later); JSON body limit 10mb on *all* routes invites oversized payloads (base64 screenshots are stored inline in `orders.payment_proof` — multi-MB rows in Postgres).
- Health endpoint broadcasts `bypassAuth` and `dbConfigured` — minor info leak; gate behind non-prod.
- Version drift: `APP_VERSION='1.3.0'`, AGENTS.md says 1.4.0, footer says v1.3.0, test hardcodes 1.3.0 — pick one source of truth (derive from `package.json`).

## 5. API Design POV

Consistent `/api/v1/*` namespacing, sensible status codes, uniform `{error}` payload shape, and good validation coverage with express-validator on writes. Specific notes:

| Area | Assessment |
|---|---|
| REST shape | Good; occasional RPC style (`/cash/confirm`, `/mark-refunded`) is acceptable for actions |
| Pagination | `page/limit` on lists; **no `limit` cap or total count** — `?limit=100000` pulls the table (sellerList with limit=200 already does big reads) |
| Error contract | Consistent `{error}`/`{errors:[]}`; webhook error path replies HTTP 200 with `{code:'FAIL'}` — verify Telebirr treats body-code (not status) as failure, else failed webhooks look delivered |
| Idempotency | Checkout has a key (broken storage, P1-3); payment initiation does not — double-tap = double Telebirr charge attempt for same order (new `txRef` each time, no guard on `payment_status='initiated'`) |
| Versioning | `/api/v1` exists; app version hardcoded in 3 places |
| Over-posting | `users/me` PUT is allow-listed (good); product PUT is allow-listed (good); `stores` update deletes secrets before response (good) — but **`GET /orders` returns `delivery_otp` and `payment_proof`** in list payloads; return only what the list view needs |
| Docs | No OpenAPI spec; the route table is discoverable only by reading code |

## 6. Security Detail (consolidated)

**AuthN/Z:** HMAC initData ✔; JWT verify on every request with fresh user lookup ✔; mock-login correctly prod-gated ✔ (with a loud warning). Gaps: delivery IDOR (P0-3), image-upload store-ownership missing (`images.js` accepts any `store_id`), phone OTP design (P1-2), seller password min-4 chars and scrypt **sync** on the event loop, no JWT revocation (device theft = 7-day access).

**Payments:** signature checked for Telebirr ✔ but bypassable via flag (P1-1); amount unchecked; manual methods trust-based (P0-2); no refund ledger (P1-4); M-Pesa merchant **secrets stored per-store** (`mpesa_consumer_secret`, `chapa_secret_key`) — at-rest protection & access audit worth confirming on Supabase.

**Webhooks:** Telegram webhook secret enforced in prod ✔; non-prod webhooks accept unsigned updates (preview deployments — an attacker who finds the preview URL can inject fake `confirm_pay_` callbacks → fake payment confirmations); scraper/search webhooks same pattern. Body-size limits apply globally (good).

**Data exposure:** PII via delivery receipt IDOR (P0-3); store order lists include buyer phone/address — fine for the owning seller only; OTP attempts logging includes the scanned order ref; CORS conflict (P0-5); no CSP (P0-4 multiplier).

**Rate limiting / abuse:** global 300/15min + auth 30/15min ✔ but in-memory; product-creation rate limit via bot ✔ (8/hour); share-coupon farming (self-reported shares mint coupons — P2); `cancel-request` spammable.

## 7. UX Paths

**Buyer:** onboarding slide → explore/search → PDP (variants, accordions, reviews) → cart per store → checkout (3 steps: address+map pin, delivery method, payment with copyable merchant codes + screenshot upload) → success w/ receipt iframe + delivery code + verification-bot deep link → orders tab w/ live polling → QR/OTP handover modal → review prompt. The path is **coherent and complete** — the cracks are: carts can hold stale fees until server re-pricing (silent UI mismatch), `switchTab('orders')` from the success screen leaves no active bottom-nav tab, and the *payment happens "instantly"* so subsequent "verify payment" messaging confuses (it reads as if payment still pending — because logically it should be).

**Seller:** role toggle → store-password gate (UX-only lock, correctly backed by `requireSellerOf` server-side) → dashboard (stats, revenue), pending (Telegram-scraped drafts → complete/publish), inventory (search/sort/edit), dispatch (rider/company/self, OTP + QR), settings (policies, payment methods, group linking). Deep-link from bot DM (`?start=complete_<id>`) into the pending modal works. Registration wizard captures payments, policies, group. Gaps: no store switcher for multi-store sellers (`State.stores[0]` is hard-wired in several spots), dashboard stats poll every 15s while visible, and "verified badge" progress exists API-side but isn't surfaced.

**Rider:** no app role — rider is a name+phone string; only the buyer/bot see them. The "rider scans" flow realistically means *the seller's device scans the buyer's QR* — fine, but then the API should reflect it (P0-3).
